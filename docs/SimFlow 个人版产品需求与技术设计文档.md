# 1. 项目背景

在日常 CAE 仿真工作中，Adams、ANSYS Mechanical、Maxwell、nCode、SolidWorks 等软件通常以文件和文件夹作为项目的主要载体。

随着仿真项目数量增加，传统文件夹管理会逐渐出现以下问题：

- 已完成项目和当前项目混在一起；
- 项目名称如果包含中文，部分 CAE 软件可能出现路径兼容问题；
- 使用日期或编号作为文件夹名称后，工程师很难直接知道项目内容；
- 项目处于“进行中”“等待试验”“等待工程师提供模型”等状态时缺乏统一记录；
- 项目何时创建、何时启动、等待了多久、何时完成、何时归档缺乏完整追踪；
- 一个仿真项目经过多轮优化后，经常出现 V1、V2、final、final_new 等混乱版本；
- 仿真项目可能在个人电脑建模，在高性能工作站求解，需要频繁人工复制；
- 本机磁盘容量有限，而工作站存储空间较大；
- 已完成项目难以形成可检索、可复用的“经典案例库”；
- 数月甚至数年之后，很难快速回答“这个项目是谁提出的”“当时为什么做”“哪个版本通过了试验”等问题。

SimFlow 的目标不是简单做一个新的文件管理器，而是建立一个围绕仿真项目生命周期设计的轻量级 **Simulation Data Management，SDM** 工具。

SimFlow 负责管理：

**项目是什么、现在做到哪里、文件在哪里、经历过哪些版本、为什么等待、什么时候完成，以及未来如何重新找到和复用。**

# 2. 产品定位

SimFlow 第一阶段定位为：

> **面向单个仿真工程师的 Windows 原生仿真项目管理与工作流工具。**

它不是：

- PLM；
- PDM；
- 网盘；
- Git 替代品；
- CAE 求解器；
- 团队任务管理系统。

第一阶段重点解决工程师个人工作效率问题。

核心价值为：

**项目管理 + 状态追踪 + 版本管理 + 存储管理 + 项目迁移 + 快速启动 + 历史检索。**

未来如果实际使用效果良好，可以逐步演进为部门或公司的仿真数据库。

# 3. 产品设计原则

## 3.1 人看到项目名称，软件看到安全路径

项目中文名称与物理目录名称完全分离。

例如：

项目名称：

```
150kA短耐动稳定性分析
```

物理目录：

```
SIM_20260916_001
```

从而保证 Adams、ANSYS、Maxwell、nCode 等软件不会因为中文路径、空格或特殊字符产生兼容性问题。

## 3.2 数据库管理逻辑，文件系统承载数据

SimFlow 不试图替代 Windows 文件系统。

项目实际数据仍然以普通文件夹形式保存。

SQLite 数据库负责：

- 项目索引；
- 搜索；
- 状态；
- 时间；
- 标签；
- 版本；
- 历史记录；
- 存储位置。

实际仿真模型、CAD、结果文件仍位于普通磁盘目录中。

## 3.3 项目状态与项目存储位置分离

项目“正在做什么”和“项目文件存在哪里”不是同一个概念。

例如：

业务状态：

```
等待中
```

等待原因：

```
等待短耐试验
```

存储位置：

```
工作站 Work
```

三者可以同时存在。

因此 SimFlow 不使用一个简单 Status 字段解决所有问题。

## 3.4 工作项目与归档项目物理分离

当前工作的项目进入 Work。

完成并正式归档后进入 Archive。

但“等待试验”的项目仍然属于 Work，而不是 Archive。

## 3.5 Archive 只有一个正式来源

个人电脑不建立正式 Archive。

正式归档统一存储于工作站共享目录。

这样避免：

```
本机 Archive
```

和：

```
工作站 Archive
```

同时存在而造成数据来源不明确。

## 3.6 一个项目原则上只有一个主副本

第一阶段不做双向实时同步。

一个项目在某一时刻只有一个正式工作位置：

- 本机 Work；
- 工作站 Work；
- 工作站 Archive。

项目可以在这些位置之间迁移，但不鼓励同时维护两个主副本。

## 3.7 SQLite 不是唯一数据源

每个项目目录必须携带自己的 `project.json`。

SQLite 是全局索引。

`project.json` 是项目自身档案。

即使 SQLite 数据库丢失，也应能够扫描所有 `project.json` 重建项目库。

# 4. 总体存储架构

推荐存储结构如下。

## 4.1 本机

```
D:\SimFlow\
│
├─ Work\
│   ├─ SIM_20260916_001\
│   ├─ SIM_20260916_002\
│   └─ SIM_20260917_001\
│
└─ AppData\
    ├─ simflow.db
    ├─ config.json
    └─ logs\
```

本机只保存当前需要在个人电脑处理的项目。

## 4.2 工作站

工作站设置一个局域网共享目录：

```
\\WORKSTATION\Simulation\
```

其内部结构：

```
Simulation\
│
├─ Work\
│   ├─ SIM_20260901_001\
│   ├─ SIM_20260903_001\
│   └─ SIM_20260912_001\
│
└─ Archive\
    ├─ 2026\
    │   ├─ 01\
    │   ├─ 02\
    │   ├─ ...
    │   └─ 09\
    │       ├─ SIM_20260901_001\
    │       └─ SIM_20260908_001\
    │
    └─ 2025\
```

工作站承担：

- 大型模型计算；
- 大容量项目存储；
- 正式归档。

个人版阶段 **无需在工作站安装 SimFlow**。

SimFlow 安装在日常个人电脑中，通过 SMB 共享路径管理工作站文件。

# 5. 存储位置模型

SimFlow 内部定义三个主要 Storage Location。

```
LOCAL_WORK
WORKSTATION_WORK
WORKSTATION_ARCHIVE
```

分别表示：

| Storage Location    | 含义           |
| ------------------- | -------------- |
| LOCAL_WORK          | 本机工作项目   |
| WORKSTATION_WORK    | 工作站当前项目 |
| WORKSTATION_ARCHIVE | 工作站正式归档 |

数据库中不建议给每个项目保存绝对路径。

推荐保存：

```
storage_location = LOCAL_WORK
relative_path = SIM_20260916_001
```

SimFlow 根据配置计算实际路径。

例如：

```
LOCAL_WORK_ROOT
D:\SimFlow\Work
```

则最终解析为：

```
D:\SimFlow\Work\SIM_20260916_001
```

如果以后工作站从：

```
\\WORKSTATION\Simulation
```

改为：

```
\\CAE-SERVER\Simulation
```

只需要修改 Storage Location 配置，不需要修改所有项目。

# 6. 项目生命周期

完整项目生命周期：

```
创建项目
    ↓
开始项目
    ↓
进行中
    ↓
可能进入等待
    ↓
恢复进行
    ↓
创建多个版本
    ↓
模型验证
    ↓
项目完成
    ↓
整理确认
    ↓
正式归档
```

其中：

“等待”和“进行”可能重复多次。

例如：

```
创建
↓
进行中
↓
等待结构工程师提供 CAD
↓
进行中
↓
等待试验
↓
进行中
↓
完成
↓
归档
```

所有状态切换都需要记录历史。

# 7. 项目业务状态

第一阶段只设置三个主业务状态：

```
ACTIVE
WAITING
COMPLETED
```

中文分别为：

```
进行中
等待中
已完成
```

不把“归档”作为业务状态。

归档属于 Storage Status。

# 8. 存储状态

存储状态：

```
WORKING
ARCHIVED
```

因此一个项目可能是：

```
业务状态：已完成
存储状态：WORKING
```

表示仿真已经完成，但还没有整理和归档。

正式归档后：

```
业务状态：已完成
存储状态：ARCHIVED
```

# 9. 等待状态

当项目进入 WAITING 时，需要填写等待原因。

第一阶段提供预设：

```
等待试验
等待CAD模型
等待工程师提供参数
等待设计方案
等待方案确认
等待评审
等待其他数据
其他
```

同时允许填写自由备注。

例如：

```
等待原因：
等待试验

等待说明：
等待9月20日150kA短耐试验结果。
```

系统自动记录：

```
wait_started_at
```

恢复项目时记录：

```
wait_ended_at
```

因此可以自动计算：

```
本次等待时长
累计等待时长
实际活动时长
```

每一个项目增加：

```

需求人
```

其含义为：

第一阶段不做人员管理系统。

需求人只是一个项目字段。

例如：

```
需求人：张三
```

未来可以扩展：

```
部门
联系方式
工号
```

但 V0.1 不做。

项目详情中需要明显显示：

```
需求人：张三
```

搜索系统应支持搜索需求人。

例如搜索：

```
张三
```

可以看到张三提出的所有仿真项目。

后续还可以统计：

```
需求人：张三
项目数量：16
进行中：3
等待中：2
已完成：11
```

但这些属于后续版本。

# 11. 时间追踪

每个项目必须支持完整时间追踪。

核心时间字段包括：

```
created_at
started_at
completed_at
archived_at
updated_at
```

分别表示：

### Created At

项目正式创建时间。

### Started At

项目第一次进入 ACTIVE 的时间。

创建项目不一定等于开始项目。

例如：

周五创建项目，下周一才开始。

因此两个时间应分开。

### Completed At

项目业务状态第一次进入 COMPLETED 的时间。

### Archived At

项目正式迁移到 Archive 的时间。

### Updated At

最后一次项目元数据发生修改的时间。

# 14. 项目版本管理

版本是 SimFlow 非常核心的功能。

统一使用：

```
V001
V002
V003
...
```

避免：

```
V2_final
V2_final_new
V3_new_final
```

每个版本包含：

```
version_number
title
description
change_summary
created_at
completed_at
status
```

例如：

```
V001
基准方案

说明：
原始设计模型

结果：
最大触头位移 2.31 mm
短耐试验不通过
V002
增加触头弹簧力

修改内容：
弹簧刚度由 8.4 N/mm 修改为 9.2 N/mm

结果：
最大触头位移 1.42 mm
V003
导电桥与弹簧联合优化

结果：
最大触头位移 0.71 mm
试验通过
```

# 15. 版本目录

项目结构（2026-09-17 定稿；完整规则见《SimFlow 项目目录结构规范》）：

```
SIM_20260917_001\
│
├─ project.json              ← 项目档案（必需）
├─ cover.png                 ← 项目封面图（可选，扩展名随原图）
│
├─ Documents\                ← 与版本无关的文档：需求单、图纸、清单、参考资料
│
├─ Versions\
│   │
│   ├─ V001\
│   │   ├─ version.json
│   │   ├─ 3D_Model\         ← 三维 / CAD：SolidWorks、x_t、STEP
│   │   ├─ CAE_Model\        ← 求解器模型：Adams、Mechanical、Maxwell、柔性体
│   │   ├─ Data\             ← 该版本输入数据
│   │   └─ Results\          ← 该版本仿真结果原始产出
│   │
│   └─ V002\                 ← 与 V001 完全同构，且必须自包含
│
└─ Delivery\                 ← 项目级对外交付物
    ├─ 仿真分析报告.docx
    ├─ Figures\              ← 报告用图表
    └─ Animation\            ← 演示动画
```

要点：

- **一个版本 = 一套自包含的模型/数据/结果**。V002 需要 V001 的模型时必须物理复制，不能用符号链接——SimFlow 的迁移遇到目录连接或符号链接会直接报错中止。
- `Documents\` 与 `Delivery\` 是**项目级**的，不随版本变化；版本内的东西进 `Versions\Vxxx\`，对外交付的东西进 `Delivery\`。
- 目录里**不放任何占位文件**；空目录由程序在迁移/复制时按源结构重建目录来保留（迁移只枚举文件，不重建的话空目录会在目标位置消失）。因此标准目录不要手工删除，程序只在创建时建一次。
- 封面图放在项目目录根部，与 `project.json` 同级，因此会随项目一起被迁移/归档复制，项目档案也自带封面，不依赖某一台电脑上的数据库。

创建逻辑位于 `ProjectService.CreateProjectDirectories` / `CreateVersionDirectories` / `CreateDeliveryDirectories`。

# 18. 项目迁移

SimFlow 的核心提效能力之一是：

```
本机 Work
→
工作站 Work
```

例如：

个人电脑进行：

- CAD整理；
- Adams初步建模；
- 参数设置；
- 小规模测试。

模型准备完成后点击：

```
移至工作站
```

SimFlow 自动完成迁移。

# 19. 项目迁移安全机制

禁止直接简单使用跨网络：

```
Directory.Move()
```

推荐流程：

```
Copy
↓
Verify
↓
Switch
↓
Delete
```

即：

### Copy

复制整个项目至工作站。

### Verify

校验目标目录。

第一阶段至少校验：

```
文件数量
目录数量
总大小
```

未来可以增加：

```
Hash
```

### Switch

校验成功后，更新数据库中的 Storage Location。

### Delete

最后删除源项目。

只有完成 Switch 后，目标目录才成为正式主副本。

如果网络中断：

- 数据库仍指向旧位置；
- 原目录不删除；
- 用户可以重新尝试。

# 21. 项目归档

项目完成后，不立即强制归档。

流程：

```
进行中
↓
已完成
↓
整理模型/结果
↓
归档
```

点击：

```
归档项目
```

自动将项目迁移至：

```
WORKSTATION_ARCHIVE
```

路径例如：

```
\\WORKSTATION\Simulation\Archive\2026\09\SIM_20260916_001
```

同时记录：

```
archived_at
```

# 22. 已归档项目恢复

未来应支持：

```
恢复项目
```

例如：

```
Archive
↓
Workstation Work
```

```
Workstation Work
↓
Local Work
```


```
WORKING
```

## 24.1 标签输入方式

标签**不采用逗号分隔的文本框**。使用 chip（标签块）编辑器：

```
标签
┌──────────────────────────────────────┐
│  #短耐 ×   #150kA ×   #动稳定性 ×     │
└──────────────────────────────────────┘
[ 输入标签后按回车添加 ]

已有标签（点击加入）
[ 短路 ] [ 机构 ] [ 疲劳 ] [ 抽屉座 ]
```

行为约定：

- 在输入框中按回车添加标签，重复标签自动忽略（不区分大小写）；
- 点标签上的 × 移除；
- 点「已有标签」中的候选项直接加入，已加入的不再出现在候选里；
- 粘贴 `短耐, 150kA` 这类内容时按逗号/分号自动拆分为多个标签——这是粘贴便利，不是界面上的分隔符约定；
- 标签允许中英文、数字和空格，去除首尾空白与开头的 `#`；
- 候选标签来自所有项目中已出现过的标签。

## 24.2 标签管理

导航「标签管理」进入标签管理页，用来整理已经散开的标签：

| 操作 | 行为 |
| --- | --- |
| 查看 | 列出所有标签及其使用项目数 |
| 重命名 | 改成一个新名称；若新名称已存在则等同于合并到该名称 |
| 合并 | 把源标签下的项目并入目标标签，然后删除源标签 |
| 删除 | 仅允许删除**没有任何项目使用**的标签；使用中的标签给出明确拒绝提示 |

约束：

- 标签名称不区分大小写唯一定义；
- 重命名/合并会改变项目实际使用的标签，因此必须同步更新受影响项目的 `ProjectTags` 关联、项目行与项目目录里的 `project.json`；
- 项目可能位于离线的工作站共享上，写 `project.json` 失败时不得让整理操作整体失败，应记录并靠启动后的元数据重试补齐；
- 标签的创建仍然发生在项目编辑里（chip 编辑器），标签管理页只做整理。

这也是 SimFlow 不使用大量文件夹分类的重要原因。

## Software

软件配置是**自定义**的：用户可以自己添加软件、改名称、改路径、改启动参数，也可以删除。不是固定七个内置软件的列表。

配置的软件清单是**软件候选项的唯一来源**：新建项目和编辑项目时的软件复选框、以及「启动软件」按钮，都读这份清单，不得在界面代码里另写一份硬编码列表。

### 数据存储位置（标准定义）

软件路径是**机器相关**配置，只保存在：

```
打包安装：%LOCALAPPDATA%\SimFlow\config.json（包外路径，卸载不会删除）
未打包调试：SIMFLOW_DATA_HOME 下的 AppData\config.json（见 Properties/launchSettings.json）
```

**不得写入项目目录的 `project.json`。** 原因：`project.json` 是项目的可移植档案，会随项目在本机 Work、工作站 Work、工作站 Archive 之间迁移。如果写入 `C:\Program Files\...\adams.exe` 这类本机路径，项目被复制到工作站或换一台电脑后就带上了一条无效路径，破坏档案的可移植性。

项目只记录“用了哪些软件”的**名称**（`software` 数组），不记录路径。因此：

| 数据 | 位置 | 是否机器相关 |
| --- | --- | --- |
| 软件名称、可执行文件路径、启动参数 | `config.json` 的 `software` 数组 | 是 |
| 项目使用的软件名称列表 | 数据库 `ProjectSoftware` + 项目目录 `project.json` 的 `software` | 否 |

### config.json 中的标准结构

```json
{
  "schemaVersion": 1,
  "localWorkRoot": "",
  "workstationWorkRoot": "",
  "workstationArchiveRoot": "",
  "simulationReportTemplatePath": "D:\\Templates\\仿真分析报告.docx",
  "checkWorkstationOnStartup": true,
  "software": [
    {
      "name": "Adams",
      "executablePath": "C:\\Program Files\\MSC.Software\\Adams\\bin\\adams.exe",
      "arguments": ""
    },
    {
      "name": "ANSYS Maxwell",
      "executablePath": "",
      "arguments": "-project {ProjectPath}"
    }
  ]
}
```

字段定义：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `name` | string，必填 | 显示名称，也是项目关联软件时使用的名字；不区分大小写唯一 |
| `executablePath` | string | 可执行文件完整路径；为空表示尚未配置，启动时给出明确提示 |
| `arguments` | string | 启动参数，支持 `{ProjectPath}` 与 `{VersionPath}` 两个占位符 |

约定：

- 软件名**不区分大小写唯一定义**；新增或改名撞到已有名称时要拒绝并提示。
- 名称是项目与软件之间唯一的关联键。删除某个软件后，历史项目档案里仍保留该名称，但无法再启动，界面需要给出明确说明。
- `{ProjectPath}` 替换为项目实际目录，`{VersionPath}` 替换为当前版本目录。
- 启动时把项目目录设为工作目录（Working Directory）。
- 软件配置页提供新建、编辑、删除；**候选清单为空时**，「新建项目」的软件复选框回落到 V0.1 的默认软件集合，避免出现既没有软件可选、又无法添加的死角。

```
默认打开方式
```

## 帮助（项目目录结构说明）

设置页提供「帮助」一节，只读展示项目目录结构，内容与《SimFlow 项目目录结构规范》一致，包含：

- 标准结构树（`project.json`、`cover.*`、`Documents`、`Versions\Vxxx\{3D_Model,CAE_Model,Data,Results}`、`Delivery\{Figures,Animation}`）；
- 「每个目录放什么」对照表；
- 必须遵守的规则：版本目录自包含（不支持符号链接）、目录里不放占位文件且空目录由程序在迁移时保留、`project.json`/`version.json` 由 SimFlow 维护不要手工改、项目目录必须是存储根的直接子目录、不要在项目内出现第二个 `project.json`、不要在项目根放自定义 `cover.*`。

完整规则见《SimFlow 项目目录结构规范》。该页不提供编辑入口，避免与创建逻辑形成第二份结构定义。

# 59. SimFlow 的核心价值总结

SimFlow 第一阶段真正要解决的不是“怎么把文件夹做得更漂亮”。

而是把传统仿真项目中散落的信息：

```
项目
文件
状态
等待
时间
版本
需求来源
计算位置
历史结果
```

统一组织起来。

最终让一个仿真项目具备完整生命周期：

```
需求产生
↓
项目创建
↓
模型准备
↓
计算
↓
等待
↓
迭代
↓
验证
↓
完成
↓
归档
↓
复用
```

SimFlow 应成为仿真工程师打开电脑以后管理所有仿真工作的统一入口，而文件夹、工作站和 CAE 软件则成为 SimFlow 背后的执行资源。
